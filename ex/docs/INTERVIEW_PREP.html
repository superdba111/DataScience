Market Pulse: Follow-up Interview Prep

About 40-minute conversation about my own solution. The topics are what works, my choices, limitations, and improvements. Keep answers short (30–60 s), then offer to go deeper.

1. Two-minute opening walkthrough

  1. Problem: traders need RT vs DA per hub and hour, and they need to know whether they can trust it. The provider re-sends rows, sends late rows and corrections, and some rows are malformed. A run that succeeds can still produce an incomplete report.
  2. Stack: Python 3.11 standard library and SQLite. There are no dependencies, so reviewers can run it in seconds. I chose this on purpose: the data is tiny and the logic is what matters.
  3. Model (3 layers): raw = the original fixture files, unchanged, identified by path, sha256 and line number. History = price_revision, append-only, with primary key (market, hub, interval_start, revision). Curated = latest_price, a view that keeps the highest revision per key. Audit = ingest_run, ingested_file and ingest_row_log, which records an outcome for every input row.
  4. Report: SQL builds a hub × hour grid first, then LEFT JOINs DA and RT. Missing data shows as NULL or count 0, never as a dropped row or a zero price. The difference is published only when RT is 4/4 and DA is present.
  5. Proof: scripts/run_demo.sh runs empty → batch_01 → batch_02 → batch_02 replay and diffs the results. Replay leaves the data byte-identical. 12 unit tests pass, and every public example and row count matches.
  6. AWS: S3 → SQS → Lambda → Aurora PostgreSQL Serverless v2, with one transaction per file, plus a scheduled completeness checker that separates "vendor late" from "pipeline late".

3. Likely questions and my answers

Data modeling and time handling (30%)

Q: Why key on interval start rather than interval end?
The contract defines the hour by interval start. If you bucket by end, the RT interval ending 00:00 lands in the 00:00 hour, which is wrong: it belongs to 23:00. I compute start = UTC(end) − duration at validation time and store it, so SQL never repeats the arithmetic. Test: test_rt_interval_ending_on_the_hour_belongs_to_previous_hour.

Q: How do you handle −05:00 vs Z?
datetime.fromisoformat parses the offset, I reject timestamps without one (naive_interval_end), convert to UTC, and store canonical text YYYY-MM-DDTHH:MM:SSZ. Every equivalent representation then collapses to one key, and string order equals time order in SQLite.

Q: Why a history table plus a view instead of UPSERT into one table?
(1) Lineage: I can explain every correction (rev 1 came from file A line 12, rev 2 from file B line 2). (2) Correctness by construction: "latest" is derived as max(revision), so neither delivery order nor a replay can undo a correction. (3) It allows as-of queries later. At production scale I'd maintain latest_price as a table, updated in the same transaction with a WHERE excluded.revision > current.revision guard.

Q: Why validate before choosing the winner?
If the blank-price rev 1 competed, a later invalid rev 3 could knock out a valid rev 2. Only valid rows enter price_revision, and rejected rows live in the log with a reason.

Q: Why not use published_at to pick the latest?
The contract says revision is authoritative. Publication clocks can be skewed and replays carry old timestamps. I keep published_at for audit.

Q: Same key and revision, different price?
It's out of scope, but I reject it as conflicting_revision and keep the first value instead of silently overwriting. In production that triggers an alarm and a conversation with the vendor.

Implementation, repeatability, tests (25%)

Q: How is replay idempotent?
Primary key (market, hub, interval_start, revision). A row whose key, revision and value are already stored is a duplicate and nothing is written. The demo diffs the hourly CSV and the latest-price CSV after the replay, and both are unchanged. Only run IDs and logs differ.

Q: What if the process crashes mid-batch?
One run is one SQLite transaction (explicit BEGIN/COMMIT). On an exception it rolls back, marks the run failed with the error, and exits with code 2. Re-running is safe. Test: test_bad_header_fails_run_and_rolls_back.

Q: How do you avoid reading batch_02 while processing batch_01?
The CLI takes --batch and reads only the files that the batch's manifest entry in scenario.json lists, joined with pathlib.

Q: How did you count replays?
Per run: rows_read, accepted_new_revision, stale_revision, duplicate, rejected. A replay shows 6 duplicates. Each file also reports previously_ingested_in_run by sha256, so an operator can see the whole file was re-sent.

Q: Which tests matter most?
Time bucketing at the hour boundary. Grid with nulls (not zeros) and the partial-hour mean. Complete RT without DA giving no difference. Older revision arriving later doesn't win. Offset-equivalent duplicates. Replay idempotency. A rejected row that is repaired later stays in history. File-level failure rolls back. Plus an end-to-end test against the public examples.

Data trust and observability (15%)

Q: How does a trader know whether to trust a number?
Every row carries rt_intervals_present/expected, rt_complete and da_available, and the difference is null unless the inputs are complete. The run summary has run_status (did the pipeline work) separate from report_status + gaps (is the data complete). Lineage columns trace each price back to file, line, sha and run.

Q: Why show an RT mean for an incomplete hour?
The contract allows it, and it's informative. The incomplete flag and the null difference stop anyone from using it as a comparison.

AWS architecture (20%)

Q: Why Aurora PostgreSQL rather than Athena/Iceberg?
The workload is small frequent writes (96 files a day, about 2–3k rows each) and narrow reads (one hub, 1–7 days). Postgres handles that with an index lookup in milliseconds, a transactional upsert, and ON CONFLICT. Iceberg would need compaction and snapshot expiry, MERGE conflicts during correction storms, and multi-second Athena latency. I'd revisit at multi-TB scale, with heavy cross-hub analytics, or if as-of time travel becomes a requirement. The first step would be a hybrid with a nightly Iceberg export.

Q: Sizing?
240k prices a day × 730 days ≈ 175M logical rows, plus revisions. That is roughly 30–50 GB with indexes, comfortably within Aurora. Monthly partitions on interval_start make 2-year retention a partition drop.

Q: How do you meet the 5-minute freshness target?
The S3 event reaches SQS and then Lambda in seconds, and processing a file takes seconds. Processing lag = committed_at − landed_at is emitted as a metric with an alarm.

Q: Vendor late vs pipeline late?
Vendor lag = now − last landed object, or missing expected intervals while no files are arriving. Pipeline lag = SQS AgeOfOldestMessage, DLQ depth, and committed − landed. If files are landed but not committed, the pipeline is at fault. If nothing has landed, the vendor is.

Q: Security separation?
The vendor role can only PutObject to landing/. The ingest Lambda role can read landing and write to the DB through IAM auth. Traders get SSO, a read-only DB role, and SELECT on report views only, with no access to raw S3. KMS encryption at rest, TLS in transit, private subnets, VPC endpoints, and no NAT. Future vendor credentials go in Secrets Manager with rotation, and CloudTrail data events are on for the bucket.

Q: Failure and recovery example?
A 14-day correction file makes the Lambda time out at 60%. The single transaction rolls back, so traders never see a half-corrected day. SQS redelivers the message, and after 3 failures it goes to the DLQ and raises an alarm. The runbook: fix the cause (timeout, or split into chunks), then redrive. That is safe because writes are idempotent. For a bug that corrupts curated data, replay raw S3 files in landing order.

Q: What's the biggest cost and what did you avoid?
Aurora ACU-hours. I avoided Redshift, EMR/Glue Spark, Kinesis, MWAA and a NAT Gateway, and set CloudWatch log retention. If Aurora's minimum capacity dominates the bill, compare it with a reserved small RDS instance.

Limitations and judgment (10%)

  • The view-based latest_price is fine at fixture scale. At scale it becomes a maintained table.
  • No as-of query yet, although the history table enables one.
  • Only the first failing validation reason is reported per row.
  • No lateness metric locally. delivered_at is recorded per run.
  • Single writer (SQLite). Concurrent writers are out of scope.
